Item Stacking mod 分析 & 优化思路
先把当前 mod 的能力盘一遍，再给可落地的优化方向。

一、当前能力总览
层面	已实现
核心机制	拖放堆叠、堆叠上限、读档补满、Ctrl+拖动整堆
合并挂点	GameItem.MayStack / GetStackSlot / SlotMarker.TryAcceptOnce（三处共用一个 MergePolicy）
决策分层	决策（MergePolicy）↔ 导流（MergeSteerer）↔ 故障标志（StackGates 三态 fail-safe）
黑白名单	容器白/黑名单（token: 裸id / slot: / owner:）、物品白/黑名单、类判据（可鉴定/赃物/未拥有/电量/动物/鼠/酒瓶/耐久/液体容器）
内置名单	代码默认 + 可选外部 item_blacklist.json（阶段5）
销毁修复	UpgradePrinter / RestoreModule / RepairExtractor / 熔炉 lambda / 密码解序器 / 拾荒口袋跨场景
其他	Alt 快移定量、整堆计价、cfg 保活、柜台禁堆、补丁自检、诊断探针
工具	内置 MiniJson 解析器（零依赖）、黑名单 id 存在性核对
做得好的地方：判据全部有 fail-safe 分级（数据保护 vs 便利）、有明确取证注释、有降级告警、有启动自检。这些都是工程性很强的实践。

二、性能问题（最值得优先做）
1. IsContainer 是热路径上的「深遍历」
csharp
var children = it?.FindAllChildItems();  // 每次合并判定都遍历全部后代
一次拖放会走 MayStack → GetStackSlot → TryAcceptOnce，Evaluate 里的 IsContainer 至少被调 2 次（target + source）× 3 挂点 = 6 次，每次都对同一物品做完整后代遍历。容器类物品（大箱子/背包）会明显卡顿。

思路：

加一层「按 (GameItem 指针, 帧号) 缓存」的 memo，命中直接返回；

或者用 WeakReference 缓存 + 内容变化时失效（更复杂，但无 frame 依赖）；

简单起点：以 Ptr(it) 为 key，Time.frameCount 为版本号缓存，一次拖放内只算一次。

2. TryGet(() => entry.xxx) 的闭包分配
MatchEmporiumSlot 里 8 个容器属性各包一个 lambda，每次合并判定分配 8 个闭包对象。热路径上 GC 压力显著。

思路：

把 8 个容器一次性读成局部变量（用内联 try/catch，不用 lambda）；

或给 TryGet 加 [MethodImpl(AggressiveInlining)] + 显式静态缓存（但不捕获变量的 lambda 才被缓存，这里捕获 entry 就不行）；

最彻底：抽一个 RefreshEmporiumSlots()，把 8 个引用打进一个 struct 缓存，按 EmporiumEntry.Instance 指针变化失效。

3. 探针在 DiagOn=false 时仍被调用
csharp
ProbeScopeInventory(TryGet(() => source?.parentInventory), "拖起方");
ProbeScopeInventory 第一行才检查 DiagOn。但传参本身已经走了 TryGet + 属性读取。ProbeNonAltMarker 同理。

思路：调用点外提 if (DiagOn)，让关闭诊断时零调用。

4. DumpCounterProbeOnce(slot.inventory) 无条件调用
GetMergeGateReason 每次都先取 slot.inventory 再进函数，函数里才判断 DiagOn。

思路：同 3，调用点外提。

5. Evaluate 结果可缓存
一次拖放 = 3 挂点 × 同一 (target, source, slotInv)，结论必然一致。用 (Ptr(target), Ptr(source), Ptr(slotInv), frameCount) 做 key 缓存 MergeVerdict + reason，第二次起直接返回。

注意：MergePolicy 里已经明确「三处结论必然一致」，这个缓存和设计意图完全吻合。

三、架构问题（中期重构）
6. Evaluate 里判据顺序硬编码，扩展性差
csharp
if (IsContainer(...)) return Deny;
var block = GetBlacklistReason(...); ...
var exclude = GetExcludeReason(...); ...
var scope = GetScopeReason(...); ...
新增一条判据要改 Evaluate，且顺序在注释里靠人肉维护。

思路：把判据做成可注册的规则对象：

csharp
class MergeRule {
    string Name;
    int Priority;
    RuleGroup Group;          // Protection / Convenience
    Func<MergeContext, string> Judge;   // 返回 null = 通过
}
Evaluate 只遍历规则表，顺序由 Priority 决定。好处：

新增规则不动框架；

顺序可单元测试验证；

规则可整体禁用（配置或故障时）。

7. WarnOnce / WarnOnceOnce / _mpFaultWarned / _warnedOnce 四套告警机制
两处一次性告警系统，容易混淆，且 WarnOnce 强制加 [防护降级] 前缀不适合所有场景。

思路：统一成一个 WarnOnce(key, msg, level)，level 决定前缀（防护降级/框架异常/探针失败）。

8. 三个销毁修复补丁结构完全重复
Patch_UpgradePrinter / Patch_RestoreModule / Patch_RepairExtractor 的 Prefix/Postfix 逻辑一模一样（拆堆 → 原版 → 归还余量）。

思路：抽一个 SplitStackWrapper<T> 泛型基类或工厂方法，三个补丁只声明「哪个参数是 electronicPart」。

9. MergePolicy.Evaluate 里 GetTagIntSafe / IsTagSafe 未 MarkJudgeFault
IsContainer / GetBlacklistReason 异常时会 MarkJudgeFault，但底层 IsTagSafe / GetTagIntSafe / GetTagStringSafe / IsSpecies 的 catch 只返回 null/false，不置故障位。

意味着：如果游戏更新导致 GetTagReadonly 失效，黑名单判据会静默放行（因为 IsTagSafe 全部返回 false → 判据"通过"）→ 数据保护悄悄消失，而 MergePolicy 以为"一切都好"。

思路：底层探针 catch 里也 MarkJudgeFault(FaultProtection)，让上层决策者知道「判据不可信」。

四、功能增强（玩家价值高）
10. 每物品堆叠上限（强烈建议）
现在 StackCap 是全局值。玩家真实需求："弹药叠 100，食物叠 10，任务物品不叠"。

思路：

新 cfg：ItemCapOverrides = "ammo_9mm:100,food_can:10"；

或外置 JSON：item_caps.json，复用现有的「默认 + 覆盖」双层结构；

挂点：MaxNumAdd Postfix 里查表，MaxNumRemove 也查（避免拆堆超上限）；

与内置黑名单共用「id 存在性核对」自检。

11. 拆堆快捷键
现在只能通过「不按 Ctrl 拖 1 个」实现拆 1。缺「拆出 N 个」的快捷操作。

思路：

Shift+右键 = 拆出 1 个到鼠标位置；

Ctrl+右键 = 拆出当前 stack 的一半；

挂点：ItemMouseDragHandler.StartDrag 里改 currentRemove（已有先例）。

12. 状态保留策略（合并时保留哪一件的状态）
现在 StackItemUnchecked 是「target.unitCount += n; source.unitCount -= n」，保留 target 的全部 tag，source 的 tag 被丢。对于「同一 id 但不同鉴定结果/电量」的物品，规则层已经拦了，但对「同 id 完全等价」的物品，保留哪一件无所谓。问题在边缘场景：比如两个同 id 但耐久度略不同的物品（如果规则层没拦住）。

思路：提供配置 MergeKeepPolicy = First | Last | HigherValue | LowerValue，在合并前检查两件的关键 tag（耐久/电量/价值），按策略决定用哪件做 target。

13. 完整的销毁路径审计
现在覆盖 6 条路径（UpgradePrinter / RestoreModule / RepairExtractor / 熔炉 / 解序器 / 拾荒口袋）。游戏里可能还有：

净水器 / 充电器 / 孵化器 / 烹饪台 / 交易台投入物品

任务提交 / 剧情消耗

报废 / 拆除

思路：反向搜索 GameAssembly 里所有 Destroy(GameItem) 调用点，逐一核对是否检查 unitCount。这是体力活，但能用脚本（dnSpy / IDA 脚本）辅助。

14. 会话统计
记录本会话：合并次数（按物品/容器）、拦截次数（按原因）、销毁修复触发次数。

思路：用 MelonPreferences 存累计，或用命令打印（MelonLoader 支持 console 命令）。玩家反馈 bug 时能直接贴统计。

五、稳定性 / 可测试性
15. 补丁熔断器
某个补丁若连续抛异常 N 次（例如游戏更新导致某方法签名变了但自检没抓到），自动禁用该补丁，避免每帧刷错误日志。

思路：PatchGuard 包一层，失败计数 > 阈值就 Harmony.UnpatchSelf() + WarnOnce。

16. 启动时自测（Smoke Test）
用假 GameItem / 假 SlotMarker 跑一遍 Evaluate 的所有分支，验证判据表完整、顺序正确。

思路：给 MergePolicy 加一个 SelfTest() 方法，在 OnInitializeMelon 里跑，只打日志不阻断。

17. 游戏版本 / RVA 校验
现在只校验方法存在性（AccessTools.Method != null），但不校验签名是否真的对。若游戏把 MaxNumAdd(SlotMarker) 改成 MaxNumAdd(SlotMarker, bool)，CheckByName 会找不到（好），但 Check 用 AccessTools.Method(t, name, args) 若游戏保留旧重载则通过——但内部实现可能变了。

思路：把关键方法的 MethodInfo.MethodHandle.GetFunctionPointer() 与一个「已知版本白名单」比对（可选，需要维护版本表）。

六、UX / 分发
18. 配置模板 / 示例
item_blacklist.json 目前只有代码注释描述格式。玩家不知道怎么写。

思路：

首次启动若 JSON 不存在，自动生成一个示例 JSON（带注释字段，或至少带所有默认组）；

生成 README_item_blacklist.md 说明字段。

19. 配置项分组
MelonPreferences 不支持嵌套，但可以按前缀约定分组（A_基础_、B_黑白名单_、C_高级_），便于玩家在 cfg 里定位。

20. 一键导出当前配置
把「生效的内置名单 + 当前 cfg 值」导出为 JSON，便于玩家分享。

八、一个容易踩的坑
MergePolicy 里的 Evaluate 已经明确「三处挂点结论必然一致」，但这依赖于 MergeContext 里的 slotInventory 在三处是同一对象。目前：

MayStack 用 __instance.parentInventory

GetStackSlot 用 __instance.parentInventory

TryAcceptOnce 用 slot.inventory

前两者是「目标物品的容器」，后者是「落点槽的容器」。在正常拖放路径下它们相等，但：

若 GameItem.parentInventory 返回 null（物品被拖起、已脱离容器）

或槽位所属容器与实际不同（嵌套背包）

就可能出现三处判定不一致。建议：在 MergeContext 构造时，让三处都把「权威容器」显式传入（目前 TryAcceptOnce 用 slot.inventory 是权威的），并在 Evaluate 里用 slotInventory 为准，不要 fallback 到 parentInventory。这样「单一源」的承诺才真正成立。
