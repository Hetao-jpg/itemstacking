## 0. 一句话模型

每个 `GameItem` 有一个 `unitCount`（int）字段，表示**这一个槽位里叠了多少个**。
"堆叠" = 把多个同 `identifier` 的 `GameItem` 合并到同一个槽位、累加 `unitCount`；
"拆分" = `GetSplitItem(requestedAmount)` 切出一部分成新 `GameItem`。

> ⚠️ **`SetUnitCount(int)` 与 `SetAmount(int)` 是同一个方法**（RVA 均为 `0x79B600`）。
> 不要误以为两者语义不同——`SetAmount` 只是 `SetUnitCount` 的别名。

## 2. ★ 关键扩展点：两套 `maxSlotAmountItemFunc` 委托体系

`maxSlotAmountItemFunc` 是"**每个格子允许的最大堆叠数**"的官方扩展点（委托返回 `int`）。
它存在于**两层**，任一层被设成更大值都可能放开上限：

### 2.1 物品层 —— `GameItemFunc`（TypeDefIndex 1361，GameItem 的基类）
`public Func<GameItem, GameInventory, SlotMarker, int> maxSlotAmountItemFunc { get; set; }`

| 委托 | 字段偏移 | getter RVA | setter RVA |

| `mayStackItemFunc` | 0x20 | 0x2BD8B0 | 0x2C2690 |

## 4. 存档 / 加载 钩子

`SaveManager`（TypeDefIndex 1527）：
- `EncodeNode(GameItem)`（0x8145E0）/ `EncodeNodes(GraphNodeStorage)`（0x815AA0）—— GameItem → SaveItemNode
- `DecodeNodes(List<SaveItemNode>)`（0x8146D0）—— SaveItemNode → GameItem（**读档重建入口**）
- `itemHeap` / `itemDict` / `currentUUID` 是静态字典，管理 uuid↔GameItem 映射

**推荐钩子链（读档改上限最稳）：**
`SaveManager.DecodeNodes` Postfix → 遍历产出的 `GameItem` → 或更直接 `SaveItemNode.OnAfterDeserialize` Postfix →
改 `SaveItemNode.unitCount`（如把存档里被压到上限的数抬高）。这样上限随存档持久化，不需要常驻运行时改写。

## 5. 注入点建议（按把握度排序）

| 方案 | 做法 | 把握度 | 风险 / 注意 |
|---|---|---|---|
| **A. 委托放开（首选）** | 给 `GameItem.mayStackItemFunc` / `GameInventory.maxSlotAmountItemFunc` 设委托返回更大值 | 高（接口公开、不改 IL） | 需确认两层取交集逻辑 [未验证]；跨 mod 若别人也设同委托需协商覆盖顺序 |
| **B. 读档改值** | `SaveItemNode.OnAfterDeserialize` Postfix 改 `unitCount` | 高（干净、持久化） | 只影响已存盘物品；新生成物品仍走默认，需配合 A 或商品生成钩子 |
| **C. 运行时改字段** | 直接 `gameItem.unitCount = N` | 中 | ⚠️ 会牵动 `unitValue/lateUnitValue/unitBaseValue` 的整体缩放，总价显示可能失真；且 `SetUnitCount` 可能含校验逻辑 [未验证] |
| **D. 改合并算法** | Harmony Patch `MayStack` / `GetSplitItem` / `TryAcceptAll` | 中 | 改行为面大；`UncheckedAccept`/`Expel` 在加载期被调用，挂点须避让加载期（见 mod开发指南 §3.1 / MEMORY 加载期网格操作铁律） |

> ⚠️ **加载期铁律（来自项目经验）**：`UncheckedAccept` / `Expel` / `SetShape` 等网格操作绝不能在
> `WorldReadyGate.ShouldDefer` 放行前跑，否则 `0x80131506` 托管 catch 抓不到的崩溃。
> 任何补丁若触碰这些路径，必须确认不在加载期触发。

## 6. 未验证项（下一步用 Ghidra / dnSpy 跟进）

> 0.4.0 复盘：下列项大多已被「反汇编取证 + 代码规避」实质解决，仅剩少量待实机确认。

1. **默认堆叠上限值** ✅ **已解决（0.3.1 反汇编实锤）**：空槽 `MaxNumAdd` 取不到
   `maxSlotAmountItemFunc` 时默认返回 **1**（即原版堆叠上限 1 的出处）；已用可配
   `StackCap` 覆盖，不强依赖该默认值。→ 跟进：无需再查。
2. **两层委托的交集规则** ✅ **已绕过**：不直接读委托，改 Postfix `MaxNumAdd` 返回值抬限。
3. **`MayStack` 的真实判定** ✅ **已绕过**：Prefix 放行同名 identifier，跳开委托 OR 聚合。
4. **合并算法** ✅ **已实锤**：`TryAcceptOnce(n)` → `n≥unitCount` 整体 `UncheckedAccept`，
   否则 `GetSplitItem(n)` 拆分 → `StackItemUnchecked(item, targetItem, n)` 合并。
5. **`SetUnitCount` 内部是否有上限 clamp** ✅ **已规避**：本 mod 从不调用 `SetUnitCount`，
   只读档改 `SaveItemNode.unitCount` 字段（不经任何 clamp 路径），未见压回。
6. **Harmony 补丁签名** ✅ **已解决**：全部目标方法用 `ilspycmd` 反编译 + `dump.cs` RVA

## 8. 实现进度（ItemStacking mod，0.2.0）

> 代码：`ItemStacking\Main.cs`；构建 `dotnet build -c Release` 0 警告 0 错误。

### 8.1 版本史

- **0.1.0（已撤销）**：`DelegateSupport.ConvertDelegate` 注入 `maxSlotAmountItemFunc`
  → `InvokeAllReduce` 反射 `Delegate.DynamicInvoke` 崩 `TargetException`。
- **0.1.1（不报错但不工作）**：只 Postfix `MaxNumAdd` 抬上限 —— 游戏拖放根本没走到
  堆叠分支（`MayStack` 恒 false，占用格直接拒绝放置），上限再大也没用。
- **0.2.0（基线）**：打开原生拖放堆叠闸门（见 8.2）。后续迭代：0.3.0 Ctrl 整堆、0.3.1 空槽容量修复、
  0.3.2 上限降到 10、0.4.0 P0/P1/P2（见 8.6）。

### 8.2 ★ 0.2.0 核心发现：EndDrag 原生就有完整堆叠机器（反汇编实锤）

`ItemMouseDragHandler.EndDrag` (0x7BA010) 落点判定顺序：

```
1. 普通放置   MayPlayerInsertInto → TryFindOneValidInventorySlot → TryAcceptOnce（×≤40 次循环）
2. ★ 堆叠分支 lastItem.MayStack(dragged)
              → lastItem.GetStackSlot(dragged)   → slot.TryAcceptOnce(currentRemove)
              （n≥unitCount 整体 Expel 移动；否则 GetSplitItem 拆分；
                最终 SlotMarker.StackItemUnchecked(item, targetItem, n) 合并）
3. 物品交互   MayTarget → CanTarget → ItemBehaviourManager.Target / GameItem.Target
```

**为什么原版不堆叠**：`MayStack`(0x799120) 与 `GetStackSlot`(0x797720) 都先对两件
物品的 `mayStackItemFunc`(0x20) 做 `InvokeAllReduce(BoolReduceOR)`，原版从未设过
→ 恒 false → 第 2 分支永不进入 → 拖到占用格被拒。

**GetStackSlot 返回值（复刻依据）**：`m = parentInventory.GetIncompleteItemInventorySlot(dragged)`
→ `m.item = dragged`、`m.targetItem = this`、`m.numTransfer = this.MaxNumAdd(m2)`。

**vtable 校准法（新方法学）**：`Slot 21 = get_childItems` 在 klass+0x288 → base=0x138
→ 0x208=Slot 13 `GetIncompleteItemInventorySlot`、0x268=Slot 19 `UncheckedAccept`、
0x278=Slot 20 `Expel` —— 与各处语义全部吻合，100% 实锤，避免靠名字猜抽象方法。

### 8.4 堆叠持久化（无需额外代码）

`unitCount` 本就序列化在 `SaveItemNode.unitCount`(0x18)：存档自动保留堆叠数量；
读档后游戏直接读字段，不经 `MaxNumAdd` 钳制，不会掉回 1。B 补满负责旧档迁移。
拆分（`GetSplitItem`）也是原生机器，剩余数量自动留回。
